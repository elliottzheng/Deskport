# 智能体网络运作方式（架构总览）

> 状态：现行架构。本文描述 Deskport 智能体网络的节点角色、通信通道、
> 任务生命周期、信任模型与扩展方式。配套文档：`agent-api.md`（接口参考）、
> `agent-kit.md`（技能包：手册 + 客户端 + 驱动）、
> `audit-agent-network.md`（质量审计）、`agent_node/README.md`（node 部署）。

一句话概括：**一个中枢（Deskport）、两种执行点（本机/远端 node）、N 个持
钥匙的指挥者（人和外部智能体），一切交互收敛到任务卡这一张监督面。**

## 一、角色与拓扑（星型）

```
                人（浏览器，cookie）
                      │ 任务卡：派活/看事件/批权限/插话/接手
                      ▼
   外部智能体 ──token──▶ Deskport 中枢（6789）──┬──▶ 本机 node（8622）──▶ 本机 Kimi
  （ai-xmyz 的 kimi 等）                        └──SSH隧道──▶ ai-xmyz node（8622）──▶ 远端 Kimi
```

- **中枢（Deskport web）**：唯一编排者。持有任务状态、审计流、权限审批、
  令牌簿（agentTokens）、节点簿（agentNodes + localAgentNodePort）。
- **agent node（每台执行机一个）**：纯粹的「会话托管者」——只认识
  `kimi acp` 协议和 HTTP token，不知道任务卡的存在。托管本机或远端的
  Kimi 会话（spawn、事件环形缓冲、权限挂起、空闲回收、resume 存档）。
- **外部智能体**：任何持有 `X-Agent-Token` 的 AI 程序。是「带钥匙的
  遥控器」，**一切指挥都经过中枢**——这是有意选择：监督面单一，
  审计与审批不旁路。（节点间理论可点对点直连，见「六、取舍」。）
- **人**：cookie 登录，拥有与智能体完全相同的能力面（派活/观察/审批/
  续聊/接手），且任务卡上所有动作可视化。

## 二、通信通道

| 链路 | 协议 | 传输 |
|---|---|---|
| 人 ↔ 中枢 | cookie + JSON / SSE | 浏览器任务卡 |
| 外部智能体 ↔ 中枢 | `X-Agent-Token` + JSON / SSE | 同一套任务 API |
| 中枢 ↔ node | `X-Agent-Token` + JSON / SSE | 直连或 SSH direct-tcpip 隧道 |
| node ↔ kimi | ACP JSON-RPC over stdio | 进程内管道 |

原则：**外部世界只看到 REST + SSE；ACP 协议只存在于 node 与 kimi 之间**。
防火墙不可达时，SSH 只承载字节流（隧道），语义仍是 HTTP + token，
零防火墙改动。

## 三、任务生命周期

1. **派活** `POST /api/tasks` → `clientFactoryFor` 选执行点
   （node=local → 本机 node；node=其它 → 指定节点 + 远端 cwd；
   本机 node 未启用 → 回退 web 内 stdio 托管）→ `_sessionThread` 建常驻会话。
2. **执行** node 侧 spawn `kimi acp`（或 `session/load` 接续存档会话）；
   中枢与 node 之间一条 **SSE 长连接**——update 到达即回调进任务卡。
   回答的 chunk 只累积缓冲（log 逐 chunk 流水可追溯），回合结束以
   **单条完整 assistant 事件**落卡——按 seq 去重的订阅者拿到的永远是终版。
3. **监督** `mode=default` 时每个工具调用停下发 `permission_request`；
   人点任务卡、或外部智能体 POST permission，决策经原路送回。
   决策提交失败会留痕（stderr + warning），node 端 900s 兜底超时。
   `mode=auto/plan/yolo` 为不同放行策略。
4. **续聊/接手** `status=waiting` 表示本轮完成；任何一方 `message` 续聊
   自动接续原上下文。多端可同时挂在同一会话上（node 按 kimiSessionId
   复用存活进程）。人可随时插话、抢权限。
5. **终局** `close` 后事件流发 `end` 关闭；任务记录持久化
   （tasks.json + log jsonl 全量流水）。

### 3.1 工作线：会话之外的那根接力棒（R5-1a）

一条工作线（如"第四轮开发"）会换很多个会话：上下文涨满、锁死、重启。
所以工作线的状态不放会话里，放三处：接力棒正文（中枢的
`worklines/<id>.md` + 任务工作区的 `WORKLINE.md` 副本）、git、规格文件。

- `POST /api/worklines` 建线；`POST /api/worklines/<id>/tasks` 派活时
  服务端把接力棒注入**首条消息**（超 4000 字则降级为摘要 + "先读
  WORKLINE.md"），并自动带上"不要使用后台任务"与 policy 摘要。
- 执行方每轮按约定把更新后的接力棒整篇写回 `WORKLINE.md`；轮末中枢比对
  hash 后落库（主控轮中改过则跳过本轮写回，单写者不覆盖）。
- 上下文超过阈值（默认 75%）落一条 status 事件，`GET /api/worklines/<id>`
  的 `nextAction=rotate` 提示；`POST .../rotate` 换新会话接棒、旧任务 close。
  默认不自动轮换（轮中切会丢半截工作）。
- 远端写回（非本机执行点 / 联邦）留到 R5-1b；联邦执行点暂不接受工作线。

## 四、韧性模型（会话为什么是「永生」的）

关键决策：**会话托管与编排分离**——web 进程不持有任何智能体会话。

| 故障 | 后果 | 恢复 |
|---|---|---|
| web 崩溃/重启 | 无感（任务活在 node 里） | watchdog 自动拉起 web |
| node 进程崩溃 | 会话中断 | kimi 自身会话存档 + `session/load` 接续；sessions.json 存档 |
| SSH/NAT 断连 | 事件流断 | 隧道自动重建 + SSE `since` 补差，零丢失 |
| 空闲 45 分钟 | node 回收 kimi 进程（省内存） | kimiSessionId 已存档，resume 接续上下文 |
| 整机重启 | 各服务由 watchdog/vbs/cron 自愈 | 本次重启已实战验证 |

## 五、信任与经济模型

- **单一信任根**：token = 全部执行权（快命令、SFTP、任务派活），无细分
  权限档位。审计是唯一制衡：`agent.exec` / `agent.sftp.*` /
  `agent.task.create` 每次调用留痕，任务卡 log 逐 chunk 可追溯。
- **权限门**：`mode=default` 让人（或指挥智能体）逐步审批；危险操作
  永远停在审批点上，直到决策或 900s 超时拒绝。
- **token 成本随成员线性增长**（每加一个指挥者/执行点分发一次）。
  这是单用户系统的有意简化：用「全程可见 + 可审计」代替「权限细分」。
  未来若出现低信任巡检类智能体需求，再拆权限档位。

## 六、取舍记录（为什么不做成别的样子）

- **星型单中枢 = 单点**。中枢挂了执行点各自存活（会话不丢），但互指
  中断；恢复后任务卡追平，无数据损失。换取：监督面永远唯一。
  对单用户这是正确取舍。
- **协议实现有意双份**（node 的 AcpSession 零依赖单文件 vs Deskport 内
  KimiAcp 回退客户端）：部署形态（拷目录即跑）与回退能力决定。
  `AcpClient` Protocol + `tests/test_acp_parity.py` 对拍测试把「双份」
  从负债变成有护栏的资产。
- **中枢内 SSE 对内 0.6s 轮询 task dict**：store 层无事件通知机制下的
  务实权衡（改造成本 > 收益）。对外/对 node 均已是推送。
- **不做多级权限 / 不做多用户**：单用户系统，负资产。

## 七、扩展方式（加成员的固定动作）

- **加一个执行点（机器）**：
  1. 目标机安装并登录 kimi CLI；
  2. 拷贝 `agent_node/` 目录；
  3. `python3 agent_node.py --port 8622 --token-file ~/.deskport-agent-node/token`
     （文件不存在自动生成）；自启：Linux 用 crontab `@reboot` + setsid，
     Windows 用 `start-agentnode.vbs` + watchdog；
  4. 中枢 `config.json` 的 `agentNodes[]` 登记一条（防火墙过滤时填
     `via` 走 SSH 隧道）。
- **加一个指挥者（智能体）**：分发 token，再把技能包整包链接给它——
  `GET /api/agent/skills/deskport/pack.zip`（带令牌）解开就是一个技能目录，
  里面的 `.deskport.json` 已填好地址；也可以单个文件自举（`GET /api/agent/skills`）。
  它立刻获得三级能力：快命令（exec）、持久终端（bash 会话）、任务派活（指挥其他
  智能体），外加现成的客户端与驱动（[agent-kit.md](agent-kit.md)）；Deskport 升级后
  重拉即同步最新版。

## 九、设计原则（网络这一层的七条）

这一层所有取舍都是下面七条推出来的，其中第 2 条已经落到代码（node 持有会话、
工作线持有接力棒），第 4、5 条是 R4 的主题。

1. **节点等价**：本机与 SSH、本机 node 与远端 node、中枢与联邦成员，对指挥者
   提供同一套接口，差别只在名字和默认值上（`host="local"` 就是这条的产物）。
2. **状态放在守护进程里，会话可以丢**：会话、事件、挂起的审批归 node；web 随时
   可重启。往下推一层——**会话无状态，状态归接力棒与仓库**（§3.1 工作线）。
3. **事件日志是唯一事实**：一条只追加、带 seq 的事件流，任何一方断线都靠「从
   seq N 继续」恢复。回放的历史必须标出来，且**永不产生可审批的事件**——曾经
   因为回放污染把一个旧审批当成新请求交给指挥者（`lessons-agent-api-feedback.md`）。
4. **委托即契约**：派活 = 规格 + 例子 + 边界。边界机器可读（`policy`）、服务端
   执行，审批只处理例外；人（和指挥智能体）不逐条盯命令。
5. **响应即上下文**：返回给指挥者的每个字节都在花它的上下文和用户的钱。默认给
   一行结论，细节按需再取，长文本标出截断与原长度；阻塞等待（`/wait`）优于轮询。
6. **会话是资产，经验进仓库**：会话可以 fork、接手、压缩，但可靠的记忆是仓库里
   的规格与接力棒文件。会话随时可能涨满、锁死、被回收。
7. **多指挥者需要协调原语**：身份（一令牌一指挥者）、配额（全局 + 按令牌）、
   归属（任务 owner）、单写者（同一 worktree 同一时间一个执行方）。

还有一条是对指挥者自己的约束：**用户的目标达成之后就停下**——剩下的想法写成
清单交给人挑，不自己立项、不自己派活。

## 十、为什么这套设计省成本

这一层最容易算错账的地方，是把「安全」当成「盯每一步」。实际经验：

- **成本主要花在误报的停止上，不在判断上**：关键词扫描会扫到命令正文（测试数据、代码
  文本），白名单也猜不准工具的真实意图，两者都会把一次执行拆成一串「停下来等批准」。
  边界交给服务端 `policy` 加客户端复判（只看真正会执行的部分）之后，介入点收敛到
  「派活、决定上线、验收」三个点。
- **会话可靠性比任何新功能都值钱**：锁不释放、回放污染、重启之后续不上，任意一条都会
  把一个任务变成几次重建。工作线（接力棒）把这部分成本从「人记得」变成「文件里有」。
- **响应体量就是成本**：一次任务详情内嵌全部事件，几个来回就把指挥者的上下文吃满。所以
  默认给一行结论、阻塞等待、事件按 `seq` 增量取。

目标值：**每个工作项介入 ≤ 2 次**，停止中真正需要判断的比例 > 50%。

## 十一、接入套件（让外部智能体真的能干活）

中枢只提供能力，能不能好用取决于客户端侧这四件东西——它们都在技能包
`.agents/skills/deskport/` 里，一次自举全拿到（说明见 [agent-kit.md](agent-kit.md)）：

- **客户端**：[`deskport.py`](../.agents/skills/deskport/deskport.py)——单文件、零依赖，
  `connect()` 一步拿到 `Host`，`Task` / `Workline` 把任务与接力棒包成对象。
- **手册 + 规矩**：`SKILL.md`（接口速查）与
  [`COLLABORATION.md`](../.agents/skills/deskport/COLLABORATION.md)（主控与执行方怎么
  分工、派活、验收），连同下面两样一起用整包自举：
  `GET /api/agent/skills/deskport/pack.zip`（带令牌，解开即用，配置按下载地址生成）。
- **边界文件**：项目自带一份 `driver.json`（可写根目录、危险命令正则、预授权档位），
  [`driver.py`](../.agents/skills/deskport/driver.py) 加载后在客户端复判命令；落在边界内
  自动放行，越界才停下来问人（原则 4 的客户端一半）。
- **别名目录**：一个任务一个 `run/<别名>/`——`msg.txt` 写规格、`last.txt` 只读一行
  结论、`state.json` 记住任务号与未送达的消息；回合中插话（服务端 409）在客户端排队，
  本轮结束自动补发。这是原则 5 在客户端侧的实现。

实测教训：worktree 只隔离**入库的文件**，未入库的 `config.json`、venv、端口都要单独
考虑（曾把 6 个测试失败误判成并行抢端口）；并行工作线各带自己的
`policy.allowPaths` / `denyCommands`，边界互不覆盖，合流由指挥者单独派一个任务。

## 十二、多智能体协作模式

两天里真实出现过的角色不止两个：一个主控、三个执行点（本机 node 与远端 node）、第二个
主控（接手另一个项目）、以及只在生产动作上出现的人。跑得起来靠的不是更多协议，而是下面
七条约定。

1. **星型，不搞网状**：执行方之间不互相派活，一切都经过中枢（§一）。换来的是可控与可
   审计；主控成为瓶颈这件事，用「边界内放行」解决，而不是让执行方点对点直连。
2. **原件只读共享**：工具、手册、令牌、驱动都只读引用原件（现在收敛成一个技能包，
   `pack.zip` 一条链接），谁都不复制一份去改；原件更新，所有主控立刻用上。
3. **薄封装 + 别名前缀**：第二个主控要改行为，就在自己目录里写薄封装（加载原件、注入
   自己的边界），任务别名加前缀（`x-`）。命令行接口对原件保持向后兼容——**原件就是共享
   接口**，改它等于改所有人的工具。
4. **边界跟着项目走**：每个项目一份 `driver.json`（可写根目录、危险正则、预授权档位）。
   同一台机器上两条工作线各有边界、互不覆盖，也就不需要互相知道对方存在。
5. **单写者**：同一份产物、同一个 worktree、同一个别名，同一时间只有一个写者。并行靠
   worktree / 目录隔离，不靠运行时协商；同一仓库可以多个 worktree，同一个 worktree 不能
   两个执行方。
6. **反馈文件是回路**：执行方不改原件，问题写进反馈文件，由人转进下一批规格。比任何实时
   通道都可靠——天然有记录、可回看、不打断执行方。
7. **合流是主控的职责**：分支各自验收通过 ≠ 合起来没问题。合并单独派一个任务，冲突取舍
   写进合并说明；跨线的判断（谁先上、要不要互相阻塞）归主控，不归执行方。

分工、派活规格、审批边界、验收与省上下文的做法，见技能包里的
[`COLLABORATION.md`](../.agents/skills/deskport/COLLABORATION.md)。
