# 构思：智能体协作的组织模型——从轮辐到公司

> 状态：构思稿（未拍板、未实施）。落盘日期：2026-11-14
> 读者：Deskport 维护者，以及**受邀评审/改进本设计的更强 AI**。为此，本文把所有
> 承重假设、证据来源、置信度、开放问题显式列出——请攻击假设，不要只改结论。
> 本文不描述已上线设施的实现细节；相邻设施只在与本模型的关系处提及。

---

## 0. 一句话

把 Deskport 的智能体协作从「主控轮辐」重构为「公司」：**用户是老板，IT 部门
（Deskport 自身）是常设部门，各项目是临时项目组，每个智能体是一名员工；员工
身份与工位（节点）正交；项目有白板，系统有白板；通信靠信箱与房间，管理靠任务卡
（mandate）。**

---

## 1. 动机：现状为什么不够

以下全部是 2026-11-13/14 实测证据，不是想象：

| # | 证据 | 暴露的问题 |
|---|---|---|
| E1 | 外部智能体（talent 主控）经 skill.zip 接入，在 ai-xmyz 上连续指挥 6 小时（B0–B4 六批、约 20 任务、5 个执行/验收会话）后提交反馈 | 单主控高负载下，**所有协调经主控中转**：实施方↔验收方无直连，主控是瓶颈；主控上下文一死，协作断 |
| E2 | 同一次高强度使用中，5 个会话「临门断气」——干完活、写报告前静默死亡；中招系统级验收三次早夭 | 主控被迫从事件流手工重建现场；**跨任务/跨角色的知识没有常驻载体**，只在主控上下文里 |
| E3 | 审计显示 `owner=kimi-code` 同时覆盖：中招办公室的活、Deskport 自身开发的活、历次冒烟测试 | **多办公室共用一个令牌身份**，审计答不出"这是谁干的"；`external-2`（talent 一办公室一令牌）是正面样板 |
| E4 | talent 项目规范教执行方「长命令后台跑」，而平台 policy 直接 deny `run_in_background` | 平台与项目规范互相打架；**平台没有"受支持的长命令模式"的官方口径** |
| E5 | 更新频繁导致旧客户端撞 breaking change（engine 字段 400）才知道落后 | 需要**版本协商**（已落地：脚本自带版本 + 响应头 stale 标记），其本质是一条**部门公告**——但当时没有"公告"这个对象，只能借响应头 |
| E6 | 智能体提反馈只能写进任务报告结尾，主控不一定翻得到 | 需要**反馈通道**（已落地：`POST /api/feedback` 令牌实名），但其形态是单向工单，不是对话 |

**结论**：缺的不是"再多一个通信管道"，而是**组织层**——身份、编组、共享状态、
生命周期。没有组织层，每加一种协作就加一对专用通道，通道之间语义重叠
（任务 message / workline 文件 / 反馈工单 / 未来的信箱），主控继续当唯一路由器。

## 2. 组织模型（比喻的精确定义）

```
用户（老板）
├── IT 部门 · Deskport（常设，不归档）
│   ├── 席位：系统管理员（发/撤令牌、联邦配置、部署重启、看全量审计）
│   ├── 常设设施：名录 / 公告板 / 系统白板
│   └── 部门令牌：维护与演化 Deskport 本身的活
└── 项目组（临时：创建 → 活跃 → 归档冻结）
    ├── 例：talent（external-2 令牌）
    └── 例：中招（应发专属令牌）
```

### 2.1 五条定义

1. **员工 = 智能体身份**。令牌即身份（可携带、跨节点有效）。一名员工可属于
   一个项目组（或部门）。身份是审计的主语。
2. **工位 = 执行节点**（local / ai-xmyz / 联邦成员）。员工今天在 ai-xmyz、
   明天在本机，**他还是他**：审计记身份，不记工位；白板跟办公室走，不跟节点走。
3. **项目组 = 持久身份 + 房间 + 白板 + 成员名册 + 任务流的集合**。任务不是
   组织单位，**项目组才是**——任务只是组内的一"班"。
4. **部门 = Deskport 自身**。常设，无归档态。拥有系统级设施，不躺进任何
   项目组的白板（可读用于审计，不写）。
5. **会话 = 工位上的草稿纸**。节点本地、当班有效、散了不可迁移；员工的长期
   记忆在白板，不在会话里。

### 2.2 身份 ⊥ 位置（承重墙）

任务已经按班次绑节点（`POST /api/tasks {node, cwd}`），"谁派"与"去哪干"是
两个字段——**API 层已拆开**。但**执行侧尚未员工化**：ai-xmyz 上跑的执行方是
一个匿名 kimi 会话，"节点上跑的是谁"不存在。补法有两案（见开放问题 Q6）。

## 3. 对象模型

| 对象 | 形态 | 归属 | 生命周期 |
|---|---|---|---|
| **令牌（员工）** | 现有 agent token + name；建议增加 `office` 归属字段 | 用户/部门签发 | 项目结束可撤；留只读档（见 Q3） |
| **项目组（office）** | 新对象：name、状态、成员令牌列表、房间地址、白板地址 | 主控创建 | 创建 → 活跃 → **归档**（房间只读、白板冻结、令牌撤） |
| **房间（room）** | 不是新设施，是**一种地址**：`to=room:<组名>` | 项目组 | 随组归档 |
| **白板（board）** | 项目级 + 系统级两块；带**稳定章节地址** | 项目组 / 部门 | 项目板随组冻结；系统板只增不减 |
| **信箱（message）** | 单一原语（见 §4） | 系统设施，按地址路由 | 未读永留；ack 后保留 30 天（可配置） |
| **名册（roster）** | 哪些组、每组有谁、谁当前在哪些节点上有活 | 部门维护 | 常设 |
| **公告（announce）** | `to=*` + kind=announce 的消息 | 部门 | 常设 |

## 4. 消息原语与寻址（信箱的本体）

```
message = {
  id, from,            # from 服务端按令牌名盖章，不可伪造
  to,                  # 令牌名 | room:<组名> | 任务id | "*"（广播）
  kind,                # note | question(带 options) | handoff | announce
  text,                # ≤N 字；不可信输入（见 §7 红线）
  ref,                 # {messageId?, taskId?, path?, url?} 回复/引用
  at
}
```

- **收信人游标**（last-seen per recipient）：drain 只拿"新到我这次看为止"。
  群聊的上下文爆炸从根上消除——**这是"房间不是新系统"的关键**。
- **一次只批一个是契约**：多选问题串行到达多个审批，driver 自动放行逐条连批
  （已文档化，不视为缺陷）。
- **跨联邦通邮 v1 不做**：消息存本 hub；联邦间是消息总线，另摊。

### 4.1 为什么不做"聊天室"

智能体是**回合制生物**：醒来、干一轮、睡下。没有"在线挂着"的常态。聊天室形态
（常驻连接、打字态、已读回执、全量历史）对回合制主体全是空转；真正需要的只有
两样：**可被寻址** + **看得到自从我上次看之后的变化**——即信箱 + 游标。房间是
寻址策略（多收信地址），不是第二套基础设施。

## 5. 白板语义

### 5.1 项目白板

- **写**：办公室内人人可写（真白板如此；写烂了有历史可追）。
- **读**：限本办公室。A 组的执行方看不到 B 组的白板。
- **形态**：结构化章节 + 稳定地址，例如 `board://talent#届模型`。mandate
  精确引用一节，而不是"最近那条"——**否则引用退化成时间戳逻辑**（这是反机械
  设计的一根支柱，见 Q4）。
- **内容**：口径、拍板决议、未决问题、决策记录（含"为什么"）。talent 的
  `设计缺陷清单-2026-11-13.md` 就是事实上的项目白板 v0（含 Q1–Q5 拍板表）。

### 5.2 系统白板

- **写**：部门（Deskport）。部分自动（构建戳、重启记录、令牌台账、联邦节点
  健康度、skill 版本），部分可由管理员手工记（已知故障、排故笔记）。
- **读**：全员可读。执行方能自查"hub 健康吗、当前 skill 什么版本"，不必问主控。
- **今天它在带外**：`.drive/上线手册.md`、队列文档、run.log——本模型要把它
  收编为一等公民。

### 5.3 记忆分层

| 层 | 载体 | 迁移性 |
|---|---|---|
| 长期记忆 | 白板（跟办公室走） | 跨节点、跨会话、跨任务 |
| 当班草稿 | kimi 会话（节点本地） | 不迁移；散了靠白板重建 |
| 点对点上下文 | 任务 mandate（主控 curation） | 随任务 |

## 6. 设计原则（承重假设，按重要性排序）

1. **系统负责"找得到和喊得应"，主控负责 curation，员工负责判断。**
   系统提供寻址/投递/可检索； mandate 是管理动作本身（"这个员工这次需要知道
   什么"写在卡里）；员工自己决定何时拉、拉多少。**系统不坐主控的椅子。**
2. **引用，不注入。** 每轮自动拼装上下文包（白板尾+未读信+名册）是消防水管：
   系统按"最近"决定重要性，可相关性是判断不是时间戳；且训练智能体 skim。
   信箱例外：**只有写给我这个人的**信，轮界到我的下次开口前送达（= 坐下先看
   自己收件箱）；白板/房间/名册一律 pull。
3. **反机械的核心是差异化卡片。** 实施方收"只写这些文件：<清单>"，验收方收
   "独立复核、不采信自述、换模型"——同项目两张卡完全不同。把员工当有分工的人，
   而不是收同一套上下文流的进程。
4. **身份 ⊥ 位置**（§2.2）。审计记身份；权限两层乘法：员工 scope × 节点政策
   （cwdRoots/主机根）。任一层否决即否决。
5. **打断只能是 warning。** 提醒（版本过期、信箱未读）不得改退出码、不得拦
   任务、不得占结论行——已落地设施（版本协商）即按此实现。
6. **消息正文与反馈正文同权：不可信输入。** 注入 prompt 时与指令分离、截断；
   任何下游不得把消息内容当命令执行。这是信箱的安全红线（feedback 红线同款）。
7. **会话是草稿纸，白板是记忆。** 不追求会话跨节点搬迁（v1 不做，见 Q5）。

## 7. 与现有机制的边界（为什么是第六个通道而不是合并）

| 现有 | 形态 | 保持不动的原因 |
|---|---|---|
| 任务 message | 主控↔本任务执行方，有轮次顺序 | 任务内专线；与信箱合并会把"谁有权给任务派活"搞浑 |
| workline 文件 | 文件态接力棒 | 项目级长期交接的白板 v0；其"尾巴注入"是小范围可用的（主控 curation 的单文件），**但不可泛化成全家桶** |
| 反馈 API | 智能体→平台，单向工单，可追进度 | 对象是"对系统的意见"，不是"给同事的话" |
| 审批漏斗 | 执行方→主控/人的授权请求 | 实时决策，不是异步通信 |
| 版本协商 | 响应头 + 脚本自带版本 | 本模型里它是**第一条部门公告**（可升级为 announce 原语的第一个用例） |

## 8. 实施顺序（依赖驱动，非愿景驱动）

| 步 | 内容 | 为什么先/后 |
|---|---|---|
| S1 | **名册**：令牌清单 + last-seen（版本协商的响应头钩子已在看每个请求，顺手记）+ 在跑任务 | 近乎免费；是信箱的发现前置 |
| S2 | **一办公室一令牌**：给中招发专属令牌；Deskport 开发活归部门令牌；config 增加 `office` 字段 | 不等任何新设施，马上让审计变干净（E3） |
| S3 | **信箱 v1**：message 原语 + 令牌/房间/广播寻址 + 游标 + driver 轮界 drain（只投点名的信） | 本模型的核心新增 |
| S4 | **项目组对象**：office 一等公民（创建/归档/成员），房间/白板挂其上 | 有了身份编组，房间白板才有归属 |
| S5 | **项目白板 v1**：结构化章节 + 稳定地址 + 历史 | mandate 精确引用的前提 |
| S6 | **系统白板 v1**：部门日志自动记（构建/重启/令牌/联邦/skill 版本）+ 手工条目 | 收编带外状态 |
| S7 | 公告原语（`to=*`）从版本头升级为真对象 | 最小一步 |

S1/S2 可立即做且无新设施风险；S3 是第一块真正的基建。

## 9. 明确不做（v1 边界，防范围蔓延）

- 实时推送（智能体回合制，轮界投递足够；SSE/wait 是主控的工具不是执行方的）
- 线程视图 / 已读回执 / 打字态（对回合制主体无意义）
- 跨联邦通邮（消息总线是另一摊）
- 会话跨节点搬迁（Q5；靠白板重建）
- 每轮自动注入任何共享状态（原则 2 禁止）
- 跨办公室通邮（v1 组间隔离，凭名录互相可见）

## 10. 开放问题（请评审 AI 重点攻击）

**Q1 房间成员制：显式订阅 vs 模糊匹配。**
显式：`room:x` 只有订阅者收到，订阅关系可管理。模糊：按"我正在忙的项目"
匹配。我倾显式（可审计、可撤销），代价是多一个成员管理面。反方观点：模糊
匹配零管理、适合临时拉群。

**Q2 白板章节寻址：地址要不要进 API 一级公民？**
`GET /api/office/<名>/board` 返回带 id 的章节树，mandate 引用 `board://<名>#<节id>`。
若章节只是时间序流，引用退化为"最近那条"。我倾向一级公民。反方：结构化
强制员工按 schema 写板，增加协作摩擦；自由文本 + 搜索也许更有人味。

**Q3 项目归档后令牌：当场撤 vs 留只读。**
留只读（可查历史任务/白板，不可建新）——复盘时"当时验收方怎么说"是常有的
追问。反方：只读令牌仍是有效凭据，归档的意义就是失效。

**Q4 谁来写"为什么"。**
白板的价值七成在决策理由（"届是一等实体，因为…"）。但执行方写板只会记
"做了什么"。要不要强制：状态推进类操作必须附一句理由（中招项目的
`status_logs` 已是此 pattern，可复用）？反方：强制理由产生敷衍文本。

**Q5 会话可迁移性到底要不要。**
v1 靠白板重建。但若某员工的判断力显著活在会话历史里（如跨 6 小时的深层
上下文），换节点=失忆。是否需要低配版：fork 时携带会话摘要（非全量）？
反方：摘要本身是损耗压缩，可能比没有更危险（自以为知道的幻觉）。

**Q6 执行侧员工化：任务卡带名片 vs 节点绑令牌。**
(a) 任务 prompt 携带员工名片（办公室/角色/权限说明），节点会话按名片扮演；
(b) 节点用绑定员工的令牌起身，会话天然是员工。(a) 便宜但名片可伪造/漂移；
(b) 干净但节点侧要管多身份。

**Q7 名册的"忙/闲"要不要做。**
从任务 owner + last-seen 能汇出。但"闲"可能是假象（员工在思考没发请求）。
做成纯事实板（"最近活跃：X 分钟前；当前在：任务 T"）还是加推断状态？

**Q8 主控多元后的话语权。**
多办公室并存时，用户是唯一老板。部门公告的强制力（如"hub 5 分钟后重启"）
如何保证被执行——公告已读回执？还是操作型公告直接配服务端行为（到期真重启）？
我倾向后者：能机器执行的别靠通知。

## 11. 假设与置信度（评审 AI 请重点核对这些）

| # | 假设 | 置信度 | 若错了怎样 |
|---|---|---|---|
| A1 | 协作瓶颈在主控中转，而非带宽/时延 | 高（E1/E2 实测） | 信箱变成没人用的摆设 |
| A2 | 智能体是回合制主体，"轮界投递+游标"够用 | 高（全部现有机制皆此形态） | 需补实时通道 |
| A3 | 每轮自动注入上下文有害（skim/水管） | 中（有 E2 的间接支持：清单式 mandate 胜过开放式；无直接 A/B） | 入职包方案复活，实施更简单 |
| A4 | 一办公室一令牌能被用户接受（多令牌管理成本） | 中（external-2 已证明可行；但用户嫌麻烦是可能的） | 退步为"至少部门与项目组分开" |
| A5 | 白板的写作纪律（写"为什么"）能靠 schema/强制部分保证 | 低（人性问题，无技术解） | 白板退化为日志，价值大减 |
| A6 | 项目组需要显式生命周期（归档）而非永久堆积 | 中 | 省掉 S4 的归档态 |

## 12. 已落地的相邻设施在本模型中的位置

- **反馈 API**（`POST /api/feedback`，令牌实名）：员工→平台的单向工单。本模型
  中保持独立；其"处理进度可追"是工单语义，不是对话语义。
- **版本协商**（脚本自带版本 + `X-Deskport-Skill-Version/Stale`）：第一条
  **部门公告**的雏形；S7 升级为 announce 原语的首个用例。
- **workline 文件**：项目白板 v0；其尾巴注入是小范围可用的主控 curation，
  不泛化。
- **审批漏斗**：实时授权，与异步通信分层。
- **联邦（win4710）**：节点/资源共享层；本模型不改变它，消息 v1 不跨联邦。

## 13. 给评审 AI 的建议攻击面

1. A3（自动注入是否有害）——这是全模型最大的单点假设，错了 §6 原则 2 和 §8
   的 S3 设计都要改。
2. Q6（执行侧员工化）——决定"员工"是只活在审计里，还是真的能带走。
3. §5.1 白板写权限（组内人人可写）与不可信输入红线（§6 原则 6）的张力：
   人人可写 + 注入即执行的风险边界到底划在哪。
4. 对象数量是否过度：office/room/board/message/roster/announce 六个新对象，
   哪些其实可以合并（例如 room 是否只是 board 的一个属性）。
5. 与现有 COLLABORATION.md 八条的关系：本模型是它的组织层扩展，还是重复造了
   一套它已经用自然语言表达的东西。
