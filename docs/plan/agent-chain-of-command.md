# 构思：指挥链——主管作为一等对象

> 状态：构思稿（未拍板、未实施）。落盘日期：2026-11-14
> 取代：[agent-collaboration-model.md](agent-collaboration-model.md)（"从轮辐到公司"）。
> 那一稿建模的是横向的"群"（办公室、房间、名册）；本稿建模纵向的"指挥链"。
> 旧稿保留作对照，§9 列出它的每一部分去了哪里。
> 文中"已核实"指对照过当前代码，"未核实"指只是推断，实施前要先验证。

## 0. 目标与衡量标准

**用户只和少数主管说话；主管指挥执行方；执行方分布在多台设备上。**

衡量标准只有一个：**用户的注意力**。每个设计点都问一句——它让用户少盯几个
会话，还是多盯几个。不减少用户交互的东西，这一稿不做。

```
用户
├── 主管 A（托管：Deskport 机器上的 kimi 会话）
│   ├── 执行方（本机）
│   ├── 执行方（ai-xmyz）
│   └── 验收方（换模型）
└── 主管 B（外部接入：例如 Claude，拿接入包自己连进来）
    ├── 执行方 …
    └── 主管 B1（可选：下一层主管，默认关闭）
```

## 1. 现状缺什么（已核实）

| 缺口 | 证据 |
|---|---|
| 系统不知道谁派了谁 | 任务只有 `owner`（令牌名），没有父任务或主管字段（`modules/tasks_api.py` 建任务处） |
| 任何全权令牌能动任何任务 | `taskRoute` 只查任务是否存在，不查归属；任务列表是全局的 |
| 主管是手工拼出来的 | 签发令牌、开会话、交接入包、交代角色、配边界，每次重做 |
| 主管只能阻塞等待 | 驱动脚本派完活停在那一轮里等；外部主控这样连续干了 6 小时 |
| 主管的记忆只在它的上下文里 | 工作线只为执行方设计；主管会话一死，协作就断（旧稿 E1/E2） |
| 并发上限只有全局一个 | `runner.maxRunning()`；一个主管能占满所有名额 |
| 令牌上限 10 个，且只存哈希 | `modules/agent_tokens.py`；每个主管一个令牌很快用完 |

已经有、可以直接用的零件：任务即常驻会话、持久化消息队列与轮界投递
（`_drainQueuedMessages`）、工作线（正文、版本、`baseRev` 冲突检测）、任务级
`policy`、能力规则模型（`modules/capability.py`）、技能包一键分发、空转轮次标记。

## 2. 核心模型：主管

**主管 = 一条持久记录 + 一个绑定的令牌 + 一份接力棒 + 一个收件箱。**
会话只是主管当前坐着的那把椅子，换会话不换主管。

```
lead = {
  id, name, project,          # project 只是标签，用于审计和分组
  kind,                       # hosted | external
  parent,                     # "human" 或上级主管 id
  taskId,                     # 仅 hosted：当前托管它的任务（轮换会话时更新）
  workline,                   # 主管自己的接力棒
  ceiling,                    # 权限与配额上限（§6）
  status,                     # active | paused | retired
  lastSeenAt, inboxSeq, cursor
}
```

三条规则把整棵树推出来：

1. **令牌绑定主管。** 鉴权时由令牌得到主管 id。
2. **用主管令牌建的任务，自动记 `task.lead = 主管 id`。** 主管侧的用法完全
   不变，树是中枢自己记出来的。
3. **主管令牌只能操作自己子树里的任务。** 这是防误伤，不是安全边界：带
   exec 权限的令牌仍可绕过，文档要明说。

主管令牌单独存放（先例：设备令牌存在 `devices.json`，经同一入口鉴权），不占
`agentTokens` 的 10 个名额。

## 3. 两种主管，一套语义

| | 托管主管 | 外部主管 |
|---|---|---|
| 是什么 | 任务卡里的常驻会话，目前是 kimi，跑在 Deskport 所在机器 | 任何拿到接入包的智能体（例如 Claude），自己跑在别处 |
| 怎么建 | 界面上一步建好 | 界面上生成接入包：技能包链接 + 一次性显示的令牌 + 角色说明 |
| 怎么收到事情 | 中枢把收件箱摘要投进它的消息队列，唤醒它 | 自己长轮询收件箱 |
| 会话归谁管 | Deskport | 它自己 |
| 用户怎么找它 | 任务卡，手机上直接说话 | 它自己的终端；Deskport 上能看到它的子树和收件箱 |

差别只在"投递方式"一列。主管记录、令牌绑定、子树、收件箱、上限对两者
完全相同。

**兼容：** 没有绑定主管的老令牌（如 `external-2`、`kimi-code`）行为不变，
仍是扁平的。外部接入这条路始终保留；要纳入指挥链，只需把令牌绑到一条主管
记录上。

## 4. 收件箱：上行汇报的唯一通道

每个主管一条只追加、带 `seq` 的日志，形状与任务事件流相同（沿用"事件日志
是唯一事实"）。v1 的条目全部由系统产生：

| 类型 | 何时产生 |
|---|---|
| `report` | 下属任务一轮结束（进入 `waiting`） |
| `failure` | 下属 `failed` / `interrupted` / 空转轮次 / 被别人关闭 |
| `escalation` | 下属的审批请求，规则判定不了（§5） |
| `human` | 用户对主管说的话 |
| `notice` | 系统提示：技能包过期、撞到配额、下属长时间无动静 |

每条是**一行结论 + 指针**（任务 id、状态、末段文本截断到 300 字），不带
正文。下属的文本一律标注为引用，不是指令。

投递：

- **托管主管**：主管处于 `waiting` 且有未投递条目时，中枢把这一批合并成
  一条摘要消息放进它的消息队列，它被唤醒处理。主管正在一轮中时，等轮界
  再投（现有机制）。合并窗口避免每个下属结束都唤醒一次。
- **外部主管**：`GET /api/leads/me/inbox?after=<seq>&wait=<秒>`，语义与
  现有任务 `wait` 相同。

**托管主管的工作方式因此改变**：醒来处理一批事 → 派活或回复 → 结束这一轮。
不再阻塞等待。这要写进主管的角色说明。

防呆：主管有未结束的下属、却超过阈值没有任何事件，产生一条 `notice`
并在用户视图里标出。

**v1 不做横向通信。** 消息只沿汇报线走：上级的话是指令，下级的汇报唤醒
上级。实施方与验收方互不直连是有意的，验收要独立（COLLABORATION §4）。

## 5. 审批沿链上行

一个下属的审批请求，依次经过：

1. 任务自己的 `policy`（现有，服务端判定）
2. **主管的常设规则**（新增：对它所有下属生效，省得每个任务重复写）
3. 主管本人判断（托管：被 `escalation` 唤醒；外部：经收件箱）
4. 用户（主管明确上交，或主管在时限内没应答）

第 4 步必须发生在超时自动拒绝**之前**。现有审批超时与托管主管的唤醒延迟
怎么配合，见 Q2。

## 6. 上限沿链收窄

`ceiling` 在建任务时由中枢强制：

- 下属的权限不超过主管的权限（复用 `capability.py` 的规则）
- 子树并发上限、子树任务总数上限
- 允许的执行点与目录根
- 是否允许再建主管；深度默认 2 层（用户 → 主管 → 执行方）
- 是否带 exec / SFTP 权限（建主管时的一个开关）

停用主管：不再接受它建新任务，可选连带关闭整棵子树。

任务总数上限同时是"目标达成就停下"的机器保障：主管被唤醒、派活、再被唤醒，
这个循环本身没有终点。

## 7. 主管的接力棒与会话轮换

每个主管一条工作线，内容是它的目标、已拍板的决定及理由、下属清单、未决事项。
"为什么"由主管写——决策不下放，本来就是它的职责。

主管上下文接近上限时轮换：新会话带上接力棒和未投递的收件箱接手。主管
id 和令牌不变，所以下属的归属不变，树不断。这是对"主控一死协作就断"的
直接回答。

约束（已核实）：工作线轮末写回目前只支持本机执行点。托管主管 v1 限定在
Deskport 所在机器，正好符合现在的用法。外部主管通过现有工作线接口带
`baseRev` 写接力棒。

## 8. 界面

遵守 `principles.md`：不加第二套导航，新建用 sheet，主管视图是任务视图的
一种分组。

**新建主管**（一个 sheet）：

- 名称、项目标签
- 类型：托管 / 外部接入
- 托管：执行点、目录、模型、职责说明
- 外部：生成接入包，给出一段可以直接粘给对方的话
- 上限：并发、任务总数、是否可再建主管、是否带 exec

**主管列表**（手机首屏能看完）：每个主管一行——状态（在忙 / 睡着 / 等你）、
下属几个在跑几个结束、等你处理几件。点开是它的收件箱、下属任务、接力棒。
用户的待办只来自主管上交的事。

## 9. 旧稿各部分的去向

| 旧稿 | 本稿 |
|---|---|
| 一办公室一令牌、`office` 字段 | 并入：令牌绑定主管，主管带项目标签 |
| 项目白板 | 并入：主管的接力棒（工作线） |
| 信箱 + 游标 | 并入：主管收件箱，只沿汇报线 |
| 公告 | 并入：收件箱的 `notice` 条目 |
| 引用不注入、打断只能是提醒、消息正文不可信 | 保留为原则 |
| 房间、名册对象、办公室生命周期、跨办公室隔离、任意寻址的消息 | 不做：没有一条减少用户交互 |
| 系统白板 | 搁置：与指挥链无关，另议 |

## 10. 实施顺序

| 步 | 内容 | 做完能得到什么 |
|---|---|---|
| P1 | 主管记录 + 令牌绑定 + `task.lead` 自动记录 + 按主管筛任务 | 审计分得清；外部主管即可纳入；行为零变化 |
| P2 | 新建主管 sheet（托管与外部）+ 角色说明模板 + 主管工作线 | 不再手工拼主管 |
| P3 | 收件箱 + 汇报触发 + 外部长轮询 + 托管唤醒与合并 + 无动静提示 | 主管不必阻塞等待 |
| P4 | 主管列表与"等你"计数 | 用户只看一屏 |
| P5 | 主管常设规则、审批上行、上限与配额、连带关闭 | 可以放心放手 |
| P6 | 主管会话轮换 | 主管不因上下文涨满而断 |

P1、P2 做完就能用。前置欠债，不解决则层数越多越跑不完：

- 会话可靠性：旧稿 E2 里约 20 个任务有 5 个临门断气；三层结构下失败率相乘
- 工作线远端写回（托管主管要放到远端执行点时才需要）

## 11. 开放问题

**Q1 默认深度。** 2 层够不够？一个可能的用法是外部 Claude 主管带几个 kimi
主管，这需要 3 层。倾向默认 2，建主管时可开。

**Q2 审批时限。** 托管主管被唤醒到作出判断需要时间，可能超过现有审批
超时。是延长子树内的超时，还是到一半时限就同时上交用户？

**Q3 托管主管的令牌怎么交到会话手里。** 客户端从环境变量或 `.agent-token`
文件读令牌；节点起会话时不注入环境变量（已核实）。倾向写文件到工作区，不
进 prompt。另外中枢目前只存令牌哈希，无法在事件流里脱敏它，也无法在轮换
会话时重新交付——托管主管的令牌是否改为中枢持有明文并登记脱敏？

**Q4 唤醒成本。** 每次唤醒是主管带着全部上下文的一轮。合并窗口多长、
摘要多短，要实测。

**Q5 主管之间。** 两个主管动同一个仓库时撞单写者原则。v1 靠用户或共同上级
协调、靠 worktree 隔离；是否需要中枢检测目录重叠并提示？

**Q6 kimi 当主管够不够。** 主管需要比执行方更强的判断力。不够的话，高要求
的项目用外部主管——这也是外部接入必须保留的原因。

**Q7 托管非 kimi 的主管。** 节点目前只托管 `kimi acp`。本稿的主管记录不
依赖具体引擎，以后节点能托管别的智能体时不用改模型。本稿不做。
