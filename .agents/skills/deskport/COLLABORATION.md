# 协作原则：主控 × 执行方

`SKILL.md` 讲接口，本文件讲**怎么用这套接口干活**。适用于任何"一个智能体指挥另一个
智能体"的场景（开发某个项目、在某台机器上运维、跑数据、做验收），不限于某个仓库。

来源：第一次驱动 Deskport 上的开发智能体时，主控逐条审批它的每个命令，结果执行方被
拆成"按键工"、主控成了瓶颈。下面每一条都是那两天踩出来的。

## 0. 一句话

**主控管两头（定义"做什么、做成什么样算完"＋独立判断"真做完了没"），执行方管中间
（怎么做）。关口要严，过程要松。**

## 1. 能力画像（分工的依据）

| 维度 | 执行方（节点智能体） | 主控 |
|---|---|---|
| 现场上下文 | 深：就在那台机器/那个项目里，熟悉环境与历史 | 浅：靠接口、读文件、它的汇报 |
| 执行成本 | 低：本地直跑、模型便宜 | 高：每步过网络、占上下文 |
| 判断力 | 通常更弱：易局部最优、易误判"完成"、自我验收放水、遇歧义脑补 | 强：设计取舍、边界情况、独立验收 |
| 典型失误 | 改了不该改的、漏边界、只测 happy path、汇报比实际乐观 | 不了解现场细节，凭推测下结论 |

推论：

- **决策不下放**：凡"有多种合理做法"的地方，由主控定死再派。
- **执行细节不上收**：具体步骤、工具用法、代码组织，让它按自己习惯来。
- **事实以它为准，结论以主控为准**：它报告的现象（文件内容、日志、版本、输出）采信；
  它给的"原因 / 已完成"必须验证。
- 画像按实际校准：遇到强的执行方可以放更大的活，弱的就切更小、关口更密。

## 2. 派活：规格要写死

每个活一条消息，结构固定：

```text
【目标】一句话
【规格】要的结果定死（接口/字段/文件格式/行为/数值口径），不留"你来定"
【例子】2–3 组 输入→期望输出（就是验收用例，也是它写回归测试的蓝本）
【边界】能动哪里 / 不能碰哪里 / 不许做的动作；一律写上"不要使用后台任务
        （run_in_background），命令都在前台运行"——后台命令会在轮次之间申请权限，
        主控看不到它要执行什么，只能拒绝，这一轮还会提前结束
【停下来问我的条件】规格与现状冲突、需要越过边界、发现规格本身有问题
【交付】改动清单/产物路径、验证结果、自评风险
```

活的粒度：

- **一次一件可独立验证的事**。多件打包 = 难审、难定位、容易顾此失彼。
- **调查和动手分开派**。调查类只读、只回报事实；原因判断和做不做由主控决定，再作为
  新活派出。
- 大活（跨多个模块/系统）先让它只出方案，批了再动手。

## 3. 执行：放手，只拦越界

审批按"边界"而不是按"每一步"：

- **自动放行**：只读操作、边界内的写、边界内的测试/检查、对非生产环境的探测。
- **停下等人**：不可逆或影响面大的动作——杀进程/重启服务、碰生产、提交/推送/回滚、
  部署、改全局配置、删数据、边界外路径、无法识别的调用。
- 过程中**不看每一步**，只看停下来的请求和最终交付；流水留日志，出问题再回查。
- **不要为了"安全"把执行方压回逐条审批**：风险靠边界控制，不靠人盯。
- **越界判定只看真正执行的部分**：heredoc 正文、引号里的字符串（测试数据、代码文本）
  里出现危险词不算越界——关键词扫描把正文也算进去，是审批太啰嗦的头号原因。
- 不能精细审批的执行方（没有审批机制、或只能全自动）：把边界前移到环境上——隔离的
  工作目录/副本、无生产权限，只在交付时把关。

两层落地：**服务端 policy**（中枢按 `allowPaths`/`denyCommands` 先放行，越界才挂起）
加**客户端复判**（驱动只看真正会执行的部分，服务端过于保守的地方本地放行）。
`driver.py` 的 `driver.json` 就是这两层的配置。

## 4. 验收：独立做，不信自述

1. **看真实产物**（diff、生成的文件、实际数据），不是看它的总结。重点：越界改动、删了
   什么、边界情况、测试是否真在断言要的行为。
2. 它自己的验证结果**只作必要条件，不作充分条件**。
3. **独立复现**：用自己的通道（API、读文件、跑命令）对着第 2 节的例子做黑盒检查。
4. **至少一条端到端用例走真实链路**：执行方的测试是用它自己构造的输入写的，输入形状
   一旦和真实系统不同，测试照样全绿。实例：319 个测试全过、20 个判定器黑盒也全过，
   但上线后第一个真实任务就暴露审批请求里根本没有参数，policy 完全没生效。
5. **每次上线后跑同一套端到端回归**，不只测本批新功能——否则老缺陷会潜伏几个小时。
6. **一条消息里有多个问题时逐条核对交付**：执行方常只做容易的几条，汇报写得很完整，
   对漏掉的那条只字不提。
7. 重要的活**换模型复核**：实施方和验收方不同模型，避免同一种盲区。

退回时给可复现的失败用例，不给感受：

```text
输入/操作：...
期望：...
实际：...
```

## 5. 上线 / 生效：分级放行

- 隔离环境（dev、副本、临时目录）：主控批准后自行生效、自测。
- 生产或对外生效（上线、发消息、覆盖原数据）：主控独立验收通过、**并向用户说明**后
  才放行；按它熟悉的流程执行。
- 生效动作可能影响主控自己的通道（比如重启我正在连的服务）时，先确认没有依赖它的
  进行中任务。
- 版本提交：验收通过后再提交。

## 6. 上下文与记忆

- **会话可丢，状态别丢**：可靠的记忆是仓库里的规格与接力棒文件，不是会话。会话随时
  可能涨满、锁死、被回收。
- **接力棒交给中枢**：`dp.create_workline(id, title, doc, policy)` 建线，之后只用
  `wl.send(text)` 说话（中枢决定投递到当前任务、排队还是开新任务），新任务首条消息自动
  带接力棒和"不用后台任务"的规则，执行方每轮结束回写 `WORKLINE.md`。`wl.info()` 的
  context/nextAction 提示该不该换会话，`wl.rotate(text)` 一步换新会话。
- **压缩执行方上下文**：每批活结束后发 `/compact`（驱动：`driver.py <别名> c`），比
  重开会话更能保留连续性；重开会话适合换方向，或会话已经出错的情况。
- **上下文膨胀会让执行方变得极慢**：同一条工作线在一个会话里接力到接近上下文上限，
  一条部署消息发出去很久都没有任何事件；换成只给规格和接力棒的新任务，同样的事几分钟
  就完成。→ 机械活（部署、重启、小修）一律新开任务；长会话只留给需要深度上下文的开发
  活，用到 50% 就 `/compact` 或换新会话。
- **经验落盘**：每批活结束时让它把经验写进项目文档（`docs/lessons` 之类），不依赖会话。
- **单写者原则**：同一份产物同一时间只有一个写者。主控要在本地改少量代码/文档时（比派活
  省），前提是不与它正在改的文件重叠，改完在下一条消息里告诉它改了哪个文件、为什么。

## 7. 中断与异常

- 任何中断（会话断开、服务重启、驱动脚本被杀）后，**第一步查状态**：任务状态、有没有
  挂着的审批、产物/仓库的实际状态。不凭记忆假设上一步成败。
- 报告与实际不符（说做了没做、说没改却改了）：拿证据指出、要求解释；反复出现就缩小
  粒度、加密关口。
- 卡住或兜圈子（同一错误反复两次以上）：让它总结已尝试路径和当前假设，主控定方向。

## 8. 什么时候主控自己做

设计、规格、验收、跨系统的判断；一次性只读查证（比派活快）；它连续失败需要换思路的
定位。其余执行性的工作交出去。

## 8b. 响应即上下文（省 token）

调用的任何程序、接口，返回值都会进主控的上下文。所以：

- **驱动/客户端默认精炼**：全量流水写日志文件，stdout 只给一行结论（`DONE 状态 + 统计
  + 最终汇报` 或 `STOP 原因 | 工具 | 命令摘要`）。要细节再去翻日志。
- **接口默认不带大字段**：事件全集、工具输出原文、日志按需取；长文本给截断版 + 总长 +
  取全文的方式。服务端做不到的，客户端先剥掉（`Task.info()` 默认剥掉 events 就是这条）。
- **让执行方的汇报也精炼**：要结论、关键证据（原始字段/数值）、需要决策的点；不要复述
  过程。规格里写明"贴原始字段，不要只写通过"，同时限定篇幅。
- **主控发出的命令本身也进上下文**：命令要短到一个词（`driver.py r4 y`）。任务 id、预授权
  正则这类固定参数放进状态文件或命名档位。
- **结果放固定的短路径**：每个任务一个短别名，`run/<别名>/` 下放 `state.json`、`msg.txt`、
  `last.txt`、`log`；读结论只需 `cat run/<别名>/last.txt`。多个任务可并行驱动，互不覆盖。
- **少轮次 > 少字节**：能一次等到结果的就用阻塞 `wait`，不要轮询；能在规格里预先授权的
  动作，就不要让它停下来问。

## 8c. 预授权：规格里点名的动作直接放行

规格里明确要它做的动作（比如"冒烟：curl 6788 建任务再 close"），审批时不应再停一次。
做法：派活时把这些命令模式加进放行规则（服务端 policy 的 `allowCommands`，或驱动
`driver.json` 的 `profiles` 档位），而不是靠通用白名单去猜。

## 9. 衡量协作好坏

- 每批活主控的介入点 ≤ 3 次（派活、审批越界、验收）。
- 一次通过率；退回时是否给了可复现用例。
- 验收通过的东西后来有没有坏——坏了说明关口漏了，补进第 4 节。

## 附录 A：踩过的坑（Deskport 自身开发，2026-11-10 至 11-12）

**工具链的痛点要优先修。** 在客户端白名单上反复打补丁（`\|` 被当管道、`timeout` 前缀、
`TOKEN=$(cat …)`、多行 `-c` 被按行拆段、引号里的危险词），前后修了六次，每次都要停下、
读输出、改代码、再批准，是那一轮最大的 token 黑洞。根因是把服务端 policy 排在了后面。
→ 客户端打补丁只能当一次性过渡。

**同一个坑踩了三次。** 用 heredoc 写含反斜杠的代码（正则里的 `\b`、`\n`）会被吞成退格符
和真换行，文件直接坏掉。→ 硬规则：**要写进文件的内容含反斜杠，就用编辑器写文件再执行**，
不要 heredoc，不要 sed 替换。

**打断自己的执行链有副作用。** 停掉驱动脚本、改代码再重启，期间那个审批没人应答，服务端
超时自动拒绝了它的修改。→ 驱动运行时不要随手停；必须停的话，重启后先查有没有超时被拒的
审批，让它重做。

**执行方会沿用旧习惯越界。** 规格写明"只提交、不部署"，它照样去执行部署。→ 写在规格里的
边界只是提醒，真正起作用的是机器执行的边界（policy + deny 规则）。

**worktree 只隔离入库的文件。** 两条分支都报"6 个失败在干净代码上也失败"，主控猜是并行跑
测试抢端口——猜错了：`config.json` 被忽略，worktree 里根本没有它。→ 环境（未入库的配置、
venv、端口）要单独考虑；主控的推测也要验证，派去查的时候写"查清是哪种原因"，不预设答案。

**用"改动真实环境"做实验会翻车。** 规格里写"把真实 config.json 临时改名、跑全量、再恢复"，
结果测试卡了 33 分钟，配置文件一直处于改名状态。→ 要找一个天然满足条件的隔离环境；所有
长命令加 `timeout`，并开 `faulthandler` 打印卡住时的栈。

**任务用完就 close。** 一天积了 21 个 paused 任务，占着 7 个进程。→ 验收通过、确定不再
续聊的任务立刻 close；运维小活建完等结果就关。

**多个主控共用一套工具时，原件就是共享接口。** 薄封装 + 别名前缀（`x-`）能并行，但改原件要
向后兼容；同一条工作线同一时间只派一个执行方。
